# EJARI — Operations, Backup, and Rollback Runbook

## النطاق

هذا الدليل خاص بمشروع `ejari-manager-next` وفرع `development`. لا يُنفذ أي تراجع على `main` أو على المستودع القديم دون موافقة صريحة.

## قبل أي نشر أو migration

يجب إنشاء نسخة احتياطية من قاعدة Supabase قبل تغيير مخطط البيانات أو تنفيذ استيراد كبير. يجب الاحتفاظ بنسخة كاملة قابلة للاستعادة، وليس الاعتماد على نسخة من الكود وحدها؛ فالكود لا يحتوي على بيانات العملاء والفواتير والقراءات والملفات المرفوعة.

يجب تسجيل commit المراد نشره، ونتيجة `npm run check`، وقائمة migrations المطبقة، ورقم النسخة الاحتياطية في سجل التغيير. يجب اختبار migration على بيئة اختبار أو نافذة صيانة مناسبة قبل تطبيقها على البيانات التشغيلية.

## استيراد CSV

الاستيراد الحالي يدعم العملاء والوحدات بصيغة CSV. يقوم النظام بقراءة الملف محلياً، ويعرض معاينة، ويتحقق من الحقول المطلوبة والقيم الرقمية والتكرار، ولا يعرض زر التأكيد الفعلي إلا عند عدم وجود أخطاء في الصفوف. عملية الإدراج دفعة واحدة؛ إذا رفضت قاعدة البيانات العملية فلن يعتمد الملف جزئياً من خلال الاستدعاء الواحد.

يجب على المستخدم الاحتفاظ بنسخة من ملف CSV الأصلي، وتجنب استيراد الملف نفسه مرتين، ومراجعة الأكواد والأرقام المرجعية قبل التأكيد. لا يجب جعل الوحدات المستوردة عامة تلقائياً؛ القيمة الافتراضية `is_public = false`.

## التراجع البرمجي

التراجع البرمجي يتم عبر Vercel باختيار deployment سابق معروف الاستقرار، أو عبر إعادة توجيه فرع `development` إلى commit سابق ثم نشر Preview للتحقق. لا يتم عمل force-push ولا إعادة كتابة التاريخ. كل commit من هذه المرحلة مستقل، ويمكن الرجوع إلى ما قبل الاستيراد عند الحاجة عبر commit `6e8b508`، وإلى ما قبل اختبارات القبول عبر `c3109ad`.

## التراجع عن البيانات

لا يُستخدم التراجع البرمجي لاستعادة بيانات حُذفت أو عُدلت. الأرشفة التشغيلية هي المسار الافتراضي للعملاء والعقود والوحدات، وتحافظ على السجل المالي. لاستعادة بيانات أوسع يجب استخدام نسخة Supabase الاحتياطية أو نقطة استعادة موثوقة وفق سياسة Supabase، مع اختبار الاستعادة على نسخة منفصلة قبل استبدال البيانات التشغيلية.

## التراجع عن migration

لا تُحذف migrations المطبقة من سجل Supabase ولا يتم تعديل migration قديمة بعد تطبيقها. عند اكتشاف مشكلة، تُكتب migration تصحيحية جديدة تعكس التغيير بأقل أثر ممكن، ثم تُختبر وتُطبق بعد أخذ نسخة احتياطية. يجب توثيق اسم migration، والسبب، والبيانات المتأثرة، وخطة التحقق.

## التحقق بعد النشر

بعد نشر Preview، يجب التحقق من فتح `/login`، حماية `/users` و`/permissions` و`/meter-types` لغير المسجلين، ظهور أزرار الاستيراد للعملاء والوحدات للحسابات المصرح لها، وتشغيل `npm run test:financial`. بعد تسجيل الدخول كمدير، يجب تنفيذ اختبار CSV صغير ببيانات اختبار فقط، ثم التأكد من ظهور صفوف المعاينة وعدم اعتماد صف خاطئ.

## Supabase Auth

يوصى بتفعيل حماية كلمات المرور المسربة من إعدادات Authentication قبل الإنتاج النهائي. تحذيرات `SECURITY DEFINER` لا تُعالج بإزالة المنح عشوائياً؛ يجب أولاً التمييز بين RPC العام المقصود لتقديم طلب التسجيل وRPC الإداري الذي يتحقق داخلياً من دور المدير. الإصلاح الآمن اللاحق هو فصل الوظائف العامة والإدارية في schema أو منحها حسب الحاجة الفعلية، ثم إعادة تشغيل مستشار الأمان.

## حالة هذا الدليل

هذا الدليل يوثق إجراءات التشغيل والتراجع؛ لا يعني أن نسخة Supabase احتياطية أو استعادة فعلية قد نُفذت داخل هذه المرحلة. يجب على مالك المشروع تنفيذ النسخة الاحتياطية الفعلية والتأكد من مكان حفظها قبل النشر النهائي.
